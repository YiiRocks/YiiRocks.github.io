Social login is built on yiisoft/yii-auth-client's OAuth2 clients rather than a hand-rolled implementation. Voyti carries no OAuth2 protocol code, and no provider configuration, of its own — providers are configured entirely through that package's own params/DI, not through any Voyti-owned option. The redirect/callback flow is handled directly by the vendor's AuthAction PSR-15 middleware, wired in Voyti's config/di.php as the voyti/session-auth route action with Voyti's own success/cancel callbacks.

Configuring providers

Two pieces are needed in the host application:

  1. A clients map under the yiisoft/yii-auth-client params key, listing which provider client classes are active.
  2. A DI definition for each listed client class, calling setClientId()/setClientSecret() (and any other setters that client exposes — scope, tenant, etc.) with real credentials.

Voyti configures each client's OAuth2 return URL for you automatically, keyed to match its own clients entry. 

// config/params.php
return [
    'yiisoft/yii-auth-client' => [
        'clients' => [
            'github' => \Yiisoft\Yii\AuthClient\Client\GitHub::class,
            'google' => \Yiisoft\Yii\AuthClient\Client\Google::class,
        ],
    ],
];
// config/di.php
use Yiisoft\Yii\AuthClient\Client\GitHub;
use Yiisoft\Yii\AuthClient\Client\Google;

return [
    GitHub::class => [
        'setClientId()' => [$_ENV['GITHUB_CLIENT_ID']],
        'setClientSecret()' => [$_ENV['GITHUB_CLIENT_SECRET']],
    ],
    Google::class => [
        'setClientId()' => [$_ENV['GOOGLE_CLIENT_ID']],
        'setClientSecret()' => [$_ENV['GOOGLE_CLIENT_SECRET']],
    ],
];

With yiisoft/config installed (the standard way to run a Yii3 app), this is all that's needed — the package's own config/di.php is merged in automatically once it's composer required. See yii-auth-client's own Quick Start guide for the full option set each client supports (custom scope via setScope(), extra auth-URL parameters, etc.).

The clients key for each provider must match that client's own getName() value — see the table below. AuthAction's success/cancel callbacks only ever receive the resolved AuthClientInterface instance, never the route's authclient value, so Voyti has no way to recover whatever key you used in clients once the OAuth flow completes. It falls back to $client->getName() instead, and persists that as UserSocialAccount::provider. If your clients key differs from getName(), login/connect still works, but "already connected" exclusion on the login page and the provider's display title both silently fall back to the raw provider string for that one provider.

Supported providers

Eight providers are supported, each backed by its own Yiisoft\Yii\AuthClient\Client\* class. Defaults (scope, endpoints) come entirely from the vendor client and its own DI wiring — see yii-auth-client's own docs for the full per-client option set.

Client\GooglegoogleStandard id/email/name claims.
Client\GitHubgithubIf /user doesn't include an email (private-email accounts), Voyti leaves email null rather than issuing a secondary request — the user supplies one manually during the registration-connect flow.
Client\LinkedInlinkedinIdentity comes from the OIDC-style sub claim rather than id.
Client\MicrosoftOnlinemicrosoftonlineHits the raw Microsoft Graph /v1.0/me endpoint (email under mail, name under displayName). Multi-tenant apps need the host's own DI wiring to also call setTenant() plus setAuthUrl($client->getAuthUrlWithTenantInserted($tenant))/setTokenUrl($client->getTokenUrlWithTenantInserted($tenant)) — the vendor client's own $authUrl/$tokenUrl defaults are literal strings containing an un-interpolated {$tenant} placeholder otherwise.
Client\FacebookfacebookThe vendor client's default requested fields don't include email; same as GitHub, Voyti leaves it null rather than issuing a secondary Graph API call.
Client\VKontaktevkontakteUses the newer VK ID endpoints (id.vk.ru) rather than the legacy oauth.vk.com/api.vk.com ones. The response has no username-like field at all — Voyti falls back to the email's local part.
Client\XxResponse is unwrapped from its data envelope. Never returns email (X API v2 doesn't expose it without elevated access).
Client\YandexyandexEmail read from default_email.

With providers configured:

  1. The login page shows social login buttons for configured providers.
  2. settings/networks/ lists connected providers and renders connect buttons for the remaining configured providers.
  3. New social identities redirect to the registration connect screen, where users can log in to an existing account or register a new one before the identity is linked.

How it works

When yiisoft/yii-auth-client isn't installed, every controller/view that touches social login (SessionController, SocialNetworkController, RegistrationController, and the login page's connect-button list) degrades gracefully: no providers are listed, and the voyti/session-auth route itself is never registered.

SocialUserAttributesNormalizer maps each provider's raw response into Voyti's canonical {id, email, username, name} shape (the vendor clients don't normalize attributes themselves). SocialAuthCallbackService — wired as AuthAction's success/cancel callbacks — then either logs a guest in via UserSocialAuthenticateService (account lookup, creation, and login) or links the identity to the current user via UserSocialAccountConnectService.

Generic self-hosted OpenID Connect identity providers aren't part of Voyti's built-in provider list. yii-auth-client ships a generic Client\OpenIdConnect class capable of real OIDC discovery and token validation — wiring one up is entirely the host application's own responsibility, configured the same way as any other client above.
